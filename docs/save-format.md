# Save format

A `.moonbase` file is JSON: `"format": "moonbase-save"`, the format `version`, the random generator's state (`random`) and the rest of the simulation state (`state`), with anything unset written as `null`. `src/simulation/save.ts` writes it and reads it back, checking every field, and `src/simulation/save-migrations.ts` holds the migrations. Saves are files the player manages; nothing is kept in the browser (ADR-0006).

## Changing the format

Each released format version is a compatibility contract:

- To change the format, raise the version and add a migration from the one before to `migrations` in `save-migrations.ts`. Never edit a released migration.
- Check in a sample save of the new version beside the old ones in `test/saves/`, where every file must go on loading. Never edit or regenerate a sample.
- New Components and bulk resources don't change the format. A save has one count for each Component and bulk resource it knew of, and from version 40 reading gives a count of none to any that a save doesn't have a count for, whatever the save's version, and puts the counts in catalogue order, so adding one needs no migration. It may go anywhere in its list.
- A count naming something the data catalogue doesn't have is refused as damaged, as any other unknown id is, so removing or renaming a Component or bulk resource still changes the format and needs a migration. Every other check stays as strict: a whole number or amount is still needed where a count is given, and a stock that isn't a list is refused. Structures built without Components, and Launch items that aren't Components (such as oxygen and water), have no counts at all.

The migrations themselves, with their comments, are the history of what each version added. Those before version 40 add a count for each new Component or bulk resource; that was how it had to be done then, and they stay as released.

## Loading older saves

Antenna fields (format version 49, data catalogue version 87) each join the radio telescope array they were placed beside, kept as `arrayId` on the field's Structure, and on its Construction while it is built. The migration from 48 gives every Structure and Construction an `arrayId` of null, as there were no fields, and the rest of a save is as it was: an array in it keeps working with its own field. Reading refuses as damaged an `arrayId` on anything but an antenna field, and an antenna field whose `arrayId` isn't a commissioned radio telescope array in the save. A save of version 49 won't load in an older game. `test/saves/version-49.moonbase` holds an array with one field commissioned beside it and a second being built beside that.

Radio telescope arrays (data catalogue version 86) keep how far each one's round of its survey has got where an infrared telescope does, as `observedMinutes` on its Structure, so they need no new saved state and the format stays at 48. Reading now refuses as damaged a Structure with `observedMinutes` above 0 that is neither an infrared telescope nor a radio telescope array. Older saves have no arrays, and load unchanged. A save holding an array won't load in a game from before it, as that game doesn't know its Structure type.

Infrared telescopes (format version 48, data catalogue version 85) keep how far each one's round of its survey has got on its Structure, as `observedMinutes`, as a Greenhouse keeps `growingMinutes`. The migration from 47 gives every Structure 0, as there were none, and the rest of a save is as it was. A Plant may now be saved as waiting for the Night (`plantStop` of `daylight`) or for something it is kept clear of to go (`too-close`), so a save of version 48 won't load in an older game. Reading refuses as damaged a Structure with `observedMinutes` above 0 that isn't an infrared telescope. `test/saves/version-48.moonbase` holds one 97 game-minutes into its round, at Night.

Automated experiments labs (format version 47, data catalogue version 84) speed up the Research Task running, so the game-minutes done of it, `workedMinutes` on `researchTask`, may now be a fraction, and a lab with no Research Task running is saved as a Plant waiting for one (`plantStop` of `no-research-task`). The lab's batch, switch and Condition are a Plant's, saved as before. Nothing in an older save changes, so the migration from 46 changes nothing: it has no labs, and its Research Task runs on at the usual rate. A save of version 47 won't load in an older game. `test/saves/version-47.moonbase` holds a lab worn below full performance speeding up a Research Task, a fraction of a game-minute into it.

The Research queue (format version 45) keeps the Research Tasks waiting behind the one running, as `researchQueue`, the next to start first. The migration from 44 gives every save an empty queue, as none could wait before, and the rest of a save is as it was. Reading refuses as damaged a queue holding one twice, the one running or one completed, or anything with nothing running. It doesn't check the queue's length or what its Research Tasks need, as those come from the data catalogue (`researchQueueLimit`, version 73) and changing them mustn't make a save unreadable: a queue longer than a lowered limit runs out as it is, and takes no more until it is shorter. A save of version 45 won't load in an older game. `test/saves/version-45.moonbase` holds a task running with two queued.

Types of Expedition (format version 46, data catalogue version 75) keep the type of an Expedition under way as `typeId` on `expedition`. Only water ice could be under way before, so the migration from 45 gives that. `test/saves/version-46.moonbase` holds a Survey under way. The Grinding line yield survey is 15 Earth Days shorter, so a save with it running when loaded finishes it sooner.

The Large-scale Crew Habitat (data catalogue version 76) doesn't change the format. Its Components are a Buried Habitat's, it is stocked from the base's oxygen and water by a water wall's rule, with no state of its own, and its Milestone comes from the Structures commissioned. A save from before it loads as it is, with the last Milestone not reached, whatever else it has reached; the celebration comes only as the Milestone is reached, never on loading.

Cumulative solar array upgrades (data catalogue version 74) don't change the format, which stays as it was. Every older kind of solar array keeps its id, so one already built, under construction or in a save stays what it was; its new Components are new ones, which need no migration. A solar array planned but not yet given its parts can become another kind after loading, if one of its parts is no longer made. A manifest in a save may hold a part no longer made: it stays, and can come off, but no more can go on.

Growing halls and vault cisterns (data catalogue version 72) don't change the format, which stays at version 44. A growing hall keeps its round in the `growingMinutes` every Structure already has, and a vault cistern is a water wall as far as the save goes, with no state of its own; their Components are new ones, which need no migration. The Grinding line yield survey is 30 Earth Days shorter, so a save with it running when loaded finishes it sooner, and a save that had already completed it can still run the Hall yield trial once it unlocks Growing halls. A save with the Optics grinding line and Lunar greenhouses unlocked can now unlock Growing halls.

The propellant limit and propellant tanks (data catalogue version 71) don't change the format, which stays at version 44: the limit comes from the Structures commissioned, a tank's Components are new ones, which need no migration, and a Plant waiting for tank space was already saved as such. A save from before them loads with its propellant as it is, however much that is, and Return Mass and Exports read it as they did. Any propellant plant then waits until the stock has fallen far enough for a batch to fit, and a batch it had started finishes and adds nothing to a stock over the limit. A save with propellant and no Plant has a limit of none and keeps it all. A save with Propellant production unlocked can now build the tank. `test/sample-saves-propellant-limit.test.ts` loads the sample of version 44 with a propellant plant and over-limit propellant edited in, as no sample saved has either.

The Greenhouse (format version 44, data catalogue version 70) keeps how far each one's round of growing has got on its Structure, as `growingMinutes`. The migration from 43 gives every Structure 0, as there were no Greenhouses, and the rest of a save is as it was. A save with Cold-trap mining unlocked can now unlock Lunar greenhouses, and offers the Closed-loop crop trial once it does. `test/saves/version-44.moonbase` holds a Greenhouse part-way through a round.

Storage tanks (format version 43, data catalogue version 69) add no saved state: a tank's limit and share come from the Structures commissioned and the stock, and what it loses is worked out within a game-minute. The format changes because two Launch items have gone, the liquid oxygen tank and the bulk water tank, and a save naming them would be refused. The migration from 42 takes them off a manifest not yet paid for, which only costs the player a choice, as no Funding has been spent. A Lander already on its way to the Moon has been paid for them, so its manifest gets the same oxygen and water as resupply items, six for each tank, which land as it would have. A save with Bulk supply tanks unlocked keeps it unlocked, and can now build the tanks. `test/saves/version-43.moonbase` holds a base with both tanks half full.

Regolith's storage limit, the bucket-wheel digger and the Regolith bin (data catalogue version 83) are data, so the format doesn't change. A save from before them loads as it is: its Regolith can't be over the heap's 2,000 kg, as digging stopped there.

Storage limits (format version 42, data catalogue version 68) change nothing that older saves hold: the limits are data, and the migration from 41 changes nothing. A Plant may now be saved as waiting for tank space, so a save of version 42 won't load in an older game. A save from before them loads with its stocks as they are, including any over a limit: the stock stays, and any Plant that makes only that stock waits until it has fallen far enough for a batch to fit. A batch it had started finishes, and adds nothing to a stock already over. Self-sufficiency's records already saved stay as they are, and time spent waiting counts from when it is loaded. `test/saves/version-42.moonbase` holds a water-processing plant waiting for tank space.

The reserve and the water an optics works and a grinding line use (data catalogue version 67) are data, so the format doesn't change, and a Plant waiting at the reserve is saved as waiting for that input, as the format already allows. A save from before them loads as it is: a batch it has started finishes on the inputs it took, with no water, and the next one takes water like any other.

A migration can only fill in what the older save recorded. When one adds state the base never kept, it says how the gap is filled. For example, saves from before version 33 kept no Milestones: the Lander departing counts as reached only if the Lander was away when the game was saved, any other Milestone whose condition the saved state already meets is reached, with its notification, in the first game-minute played after loading, and the First Export counts from the next sale. Saves from before version 41 kept no record of spare Components, so a whole Lunation has to pass after loading before the base can be self-sufficient in them.

A save from before Act 2 was in the game, with all nine of Act 1's Milestones reached, needs no migration for it: the Act comes from the Milestones reached, so it loads straight into Act 2, with no notification, as no Act's start is announced on loading a save. Its Act 2 Milestones are reached from then on like any others, in the first game-minute they hold. Acts 3 and 4 are the same: a save with every Milestone of the Acts before reached loads straight into the next.
